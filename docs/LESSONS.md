# 《無名旅人的星光之路》經驗整理

整理於 2026-11-14。這份文件記錄這個專案做對的事、沒做好的事，以及留給下一個作品（可互動劇情、導入生成式 AI）的規劃。下一個作品會在新的專案裡開發，這份文件是給那時候參考用的。

## 一、架構上做對的事

- **純靜態、零依賴**：只有 HTML、CSS、JS，沒有建置步驟。直接開檔案就能玩，推上 GitHub Pages 就能發布。
- **內容和邏輯分開**：劇情、角色、道具、謎題全在 `adventure/story.js`，遊戲規則在 `adventure/game.js`。改劇情不需要碰程式，檔案開頭有欄位說明。
- **素材不存在時自動退回**：圖片有就顯示，沒有就用預設圖或純文字（`game.js` 的 `probe`、`optionalImage`）。可以先把遊戲做完再一批一批補圖，中途任何時候遊戲都能玩。這是整個專案能小步前進的關鍵。
- **手機直式優先**：先決定畫面是直式，桌機只是置中顯示同一個直式畫面。版面、圖片尺寸和安全區都只需要考慮一種情況。

## 二、AI 產圖的流程

圖片由 codex CLI 的內建圖片生成工具產出，後續加工由 Python（Pillow）處理。

### 做法

1. **先寫素材清單**：`ART_TODO.md` 事先寫好每張圖的路徑、尺寸、共通風格和禁止事項。產圖的提示直接從清單組出來，風格才會一致。
2. **用 `codex exec` 非互動呼叫**，一次交代一批圖，放在背景執行（9 張小圖或 7 張背景各約數分鐘）：

   ```
   codex exec --sandbox workspace-write -i assets/starlight.png -o <報告檔> "<提示>"
   ```

   - `-i` 附上參考圖來定畫風。
   - 提示裡要求「必須用圖片生成工具，不可以用程式畫」「不要修改其他檔案」「完成後列出每個檔案的尺寸」。
   - 產出的 PNG 存到 `assets/_gen/`（已加入 `.gitignore`），保留原圖方便日後重新加工。
3. **加工**：依透明區域裁切、補成正方形、縮放、轉 WebP（品質 80–85）。背景裁成 9:16 再縮放到 1080×1920。

### 讓提示有效的寫法

- **把畫面安全區寫進提示**：上方 12% 會被資訊列蓋住，只放天空；主體放在 12%–60% 的高度；下方 32% 會被對話框蓋住，只放地面；主體放在中間 75% 的寬度內。這次 7 張背景都不需要重做。
- **世界設定寫成硬性規則並重複強調**：「天空沒有星星」放在規則區，7 張都遵守了。
- **成對的圖要求形狀和角度一致**：例如亮、暗兩盞燈籠。
- **需要旋轉使用的圖要指定方位**：角花只畫左上角，另外三個角由 CSS 翻轉。

### 踩到的問題

- **透明圖可能帶一層霧**：角花的原圖有半透明的灰白底，用程式只保留金色像素才乾淨。
- **產出的尺寸不是指定的尺寸**：直式背景實際是 941×1672，需要放大到 1080×1920。
- **遠景會自己加東西**：幾張背景多畫了亮燈的城牆，和「人煙稀少」的設定有出入。提示裡應該明確寫出遠景可以有什麼、不能有什麼。
- **小圖示不要用生成圖**：選單和按鈕的圖示改用內嵌的 SVG 線條圖，小尺寸下比較清楚。
- **不搭的底圖可以重新上色而不必重產**：羊皮紙紋理轉灰階後上色成深藍，成為現在的手札紙頁。

## 三、設計決策的過程

- **先看實際畫面再給建議**：截圖之後才看出信任值的細線幾乎看不見、道具沒有存在感。
- **用可丟棄的試作來決定方向**：羊皮紙手札直接做出來看，發現和夜景不搭，一次調整就改成深藍紙頁。比事先討論更快得到答案。
- **試作的成果盡量沿用**：排版、道具圖示和紙張紋理都留了下來，只換了配色。
- **在工作分支上試作**，確認後再合併進 `main`。
- **每次改動都在手機尺寸（390×844）下截圖檢查**，包含有道具、沒道具、圖片缺失三種狀態。

## 四、沒做好的地方

- **美術太晚開始**：遊戲很長一段時間每一幕都是同一張圖，而且那張圖有星星，和劇情矛盾。下次在劇本定稿時就先產背景。
- **選擇沒有取捨**：支線沒有代價，最佳玩法就是全部都做。真結局需要信任 2，而全遊戲只有兩處能加信任，等於只有一條固定路線。下次每個選擇都應該讓玩家放棄一些東西。
- **道具用途重疊**：提燈和光葉都只用來解鎖壁畫，而真結局必須拿光葉，提燈可有可無。每件道具應該有只有它能做到的事。
- **謎題太少也太簡單**：只有一個排序謎題，石板上的文字本身就是答案。
- **結局不回應玩家做過的事**：三個結局的文字固定，角色也沒有再出現。
- **沒有重玩的動機**：缺少結局紀錄和標題畫面。
- **規模小**：12 個段落、約 55 句台詞，一輪大約 5 分鐘。

## 五、給下一個作品：生成式 AI 互動劇情的規劃

### 前提

靜態網站沒有伺服器，而呼叫模型需要金鑰，金鑰不能放在網頁裡。評估過四種做法：

| 做法 | 結論 |
|---|---|
| 事先生成大量分支，每輪隨機抽 | 不需要伺服器，但玩家不能自由互動 |
| **即時生成，經過自己的小型後端** | **選用這個** |
| 模型跑在玩家的瀏覽器裡 | 要下載 1GB 以上的模型，手機跑不動 |
| 玩家自己填金鑰 | 訪客不會願意 |

### 架構

```
玩家的瀏覽器（靜態前端）
      │  傳送：目前場景、進度摘要、玩家的行動
      ▼
小型後端（保管金鑰、限制用量、檢查輸入）
      │
      ▼
AI 模型 → 回傳固定格式：台詞 + 有限的結果
      │
      ▼
遊戲程式檢查結果是否合乎規則，再演出
```

### 設計原則

- **由人寫死**：世界設定、關鍵事件、道具、結局條件、謎題。
- **由 AI 生成**：角色的自由對話、路上的隨機遭遇、對玩家行動的描述。
- **規則留在程式裡**：AI 只能回傳固定格式（台詞，加上「信任 +1」「給予道具」「可前往的地點」這類有限的結果），由程式決定是否採用。AI 不能直接改遊戲狀態。
- **場景和立繪從固定清單裡選**：AI 不能發明沒有圖的地點。
- **AI 連不上或超過用量時，退回寫好的劇本**，遊戲仍然玩得完。

### 初步的技術選擇（尚未驗證）

- 後端：Cloudflare Workers。
- 模型：Claude 的小型模型，優先考慮速度和單價，文筆不夠再換大的。
- 用量：每位訪客每天的互動次數有上限，整體每月支出也有上限。

### 主要風險

- **費用**：網站公開，必須限制用量。
- **等待時間**：每次生成估計 1 到 3 秒，可以用逐字顯示掩蓋一部分。
- **一致性**：每次都要把世界設定和目前進度傳給模型，並檢查輸出。
- **內容安全**：開放自由輸入就要處理離題和惡意輸入。

### 建議的階段

1. **試驗**：只讓一個角色可以自由對話，信任值從對話中獲得，聊完接回固定劇情。用來確認效果、等待時間和實際花費。
2. **開放的旅途**：地點之間可以來回，每個地點有生成的隨機遭遇。
3. **結局回應旅程**：結局文字依玩家實際做過的事改寫。

### 尚未決定

玩家的互動方式：

- AI 生成選項，點選即可：手機上最順，但只能從選項裡挑。
- 自由輸入：最開放，但手機打字慢，要處理惡意輸入。
- 兩者並用（當時的建議）：三個生成的選項，加一個可以打字的「自己說……」。
